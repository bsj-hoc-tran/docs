🎯 Clean Architectureの概要

Clean Architectureは、関心の分離（separation of concerns）を目的としたソフトウェアアーキテクチャであり、保守性、拡張性、テスト容易性の高いシステムを構築します。このプロジェクトでは、これらの目標を達成するために、Layered ArchitectureとRepository Patternを組み合わせて適用しています。

コア原則

🔄 Dependency Inversion

レイヤーは具体的な実装ではなく、抽象化（インターフェース）に依存する

🎯 Single Responsibility

各クラスは単一の責任のみを持つ

🔀 Separation of Concerns

各レイヤーはアプリケーションの特定の側面のみを処理する

✅ Testability

依存性注入を通じて各レイヤーを独立してテストできる

📦 Repository Pattern

Repository Patternは、ビジネスロジックとデータアクセスレイヤーの間に抽象化レイヤーを提供するデザインパターンです。

🔒 ビジネスロジックとデータベースの分離

Serviceはデータベースクエリの詳細を知る必要がない

🔄 データソースの変更が容易

EloquentからMongoDB、APIなどに変更してもServiceに影響しない

✅ テストが容易

ユニットテストでRepository Interfaceをモックできる

Repository Interface (Contract)
↑ implements
Repository (Eloquent Implementation)
↓ uses
Model (Eloquent Model)

📚 各レイヤーの詳細

1 Resource Layer (APIレスポンス整形)

場所: app/Resources/PostResource.php

役割: API経由でクライアントに返す前にデータを整形する

✅ 許可される処理

  • whenLoaded()、mergeWhen()を使用した条件付きロード
  • データのフォーマット（datetime、boolean変換）
  • 事前にロードされたリレーションへのアクセス
  • リスト用のResourceCollectionの作成

❌ 絶対禁止事項

  • ビジネスロジック（例：ポイント計算、ステータス変更）
  • 直接的なDBアクセス
  • Serviceメソッドの呼び出し
  • トランザクション処理
// app/Resources/PostResource.php
class PostResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id' => $this->resource->id,
            'content' => $this->resource->content,
            'is_published' => boolval($this->resource->is_published),
            
            // 条件付きデータ
            'poster' => $this->when($this->withPosterData, function() {
                return $this->getPosterDetails();
            }),
        ];
    }
}

2 Controller Layer (HTTPリクエスト処理)

場所: app/Http/Controllers/PostController.php

役割: HTTPリクエストのエントリーポイント、HTTP固有の関心事を処理

✅ 許可される処理

  • 例外をキャッチするためのtry-catch
  • 見つからない場合のabort(404)
  • カスタムレスポンスのためのresponse()->json()
  • HTTP例外のスロー（ForbiddenExceptionなど）
  • リクエストからの情報抽出（user ID、admin IDなど）

❌ 絶対禁止事項

  • ビジネスロジック（例：複雑なバリデーション、計算）
  • Eloquentの直接呼び出し（Post::where(...)）
  • 直接的なSQLクエリ
  • 手動でのValidator作成
  • トランザクション管理
// app/Http/Controllers/PostController.php
public function store(CreatePostRequest $request): PostResource
{
    // 権限チェック（HTTP関心事）
    if (!RolePermissionService::isAcceptable(...)) {
        throw new ForbiddenException(...);
    }
    
    // Serviceに委譲
    $post = $this->postService->createPost($inputs, $adminUuid, $userId);
    
    return new PostResource($post);
}

3 Request Layer (入力バリデーション)

場所: app/Http/Requests/CreatePostRequest.php

役割: HTTPリクエストからの入力パラメータをバリデーション

✅ 許可される処理

  • バリデーションルールを定義するrules()メソッド
  • エラーメッセージをカスタマイズするmessages()メソッド
  • 権限をチェックするauthorize()メソッド
  • シンプルなバリデーションルール（required、integer、date、string、inなど）
  • 配列バリデーション（media_ids.*.id）

❌ 絶対禁止事項

  • 直接的なDBアクセス
  • 複雑なビジネスロジックバリデーション
  • exists:posts,idなどの重いバリデーションルール（Ruleクラスを使用すべき）
  • トランザクション
  • Serviceの呼び出し

📌 Ruleクラスを使用する場合

  • バリデーションでデータベースをクエリする必要がある場合
  • バリデーションが複雑で、ビジネスロジックを含む場合
  • バリデーションで複数のソースからのコンテキストが必要な場合
// app/Http/Requests/CreatePostRequest.php
public function rules(): array
{
    return [
        'is_published' => ['boolean', 'nullable'],
        'type' => ['required', 'string', 'in:free,premium'],
        'published_start_at' => ['nullable', 'date_format:Y-m-d H:i:s'],
        'published_end_at' => ['nullable', 'date_format:Y-m-d H:i:s', 'after:published_start_at'],
        'content' => ['nullable', 'string'],
        'media_ids' => ['array'],
        'media_ids.*.id' => ['required_with:media_ids', 'string'],
    ];
}

4 Rule Layer (複雑なバリデーション)

場所: app/Rules/（存在する場合）

役割: データベースクエリやビジネスロジックが必要な複雑なバリデーションを処理

✅ 許可される処理

  • 条件をチェックするためのDBクエリ
  • ビジネスロジックバリデーション
  • コンテキストへのアクセス（user、companyなど）

❌ 絶対禁止事項

  • トランザクション
  • データ更新（読み取りのみ）
  • メール送信、通知
  • 副作用
// app/Rules/UniqueInCompany.php
class UniqueInCompany implements Rule
{
    public function passes($attribute, $value)
    {
        // 会社スコープ内でユニークかチェック
        return !Post::where('company_id', $this->companyId)
            ->where('title', $value)
            ->exists();
    }
    
    public function message()
    {
        return 'The title has already been taken in this company.';
    }
}

5 Service Layer (ビジネスロジック)

場所: app/Services/PostService.php

役割: ビジネスロジックとユースケースの中心

✅ 許可される処理

  • beginTransaction()、commit()、rollback()
  • 複数のRepositoryの呼び出し
  • 他のServiceの呼び出し
  • ドメイン例外のスロー
  • ビジネスロジック（計算、複雑なバリデーション）

❌ 絶対禁止事項

  • Eloquentの直接呼び出し（Post::where(...)）
  • 直接的なSQLクエリ
  • HTTPレスポンスの返却
  • レスポンスデータのフォーマット
public function createPost(array $params, string $adminUuid, int $userId): Post
{
    // ビジネスロジック: ポスターの存在確認
    $poster = $this->posterRepository->getPosterByUserId($userId, $adminUuid);
    if (!$poster) {
        throw new ResourceNotFoundException(...);
    }
    
    try {
        // トランザクション管理
        $this->postRepository->beginTransaction();
        $post = $this->postRepository->create(new Post(), $params);
        $this->associateMediaWithPost($post->id, $params['media_ids'] ?? []);
        $this->postRepository->commit();
    } catch (ConflictException|ResourceNotFoundException $e) {
        $this->postRepository->rollback();
        throw $e;
    }
    
    return $post;
}

6-7 Repository Layer

Interface: app/Repositories/PostRepositoryInterface.php

Implementation: app/Repositories/PostRepository.php

✅ 許可される処理

  • Eloquentクエリ（where、with、cursor）
  • クエリ構築
  • リレーションの事前ロード
  • キャッシング
  • クエリのロギング

❌ 絶対禁止事項

  • ビジネスロジック
  • トランザクション管理（Serviceが行う）
  • HTTP関心事
  • レスポンスデータのフォーマット

8 Model / Entity Layer

場所: app/Models/Post.php

役割: データベーステーブルを表し、テーブルと1対1でマッピング

✅ 許可される処理

  • $fillable、$casts
  • リレーション（belongsTo、hasMany）
  • スコープ（scopeActive）
  • Accessors/Mutators
  • 定数

❌ 絶対禁止事項

  • ビジネスロジック
  • Serviceロジック
  • 複雑な静的メソッド
  • 複雑なDBクエリ
  • トランザクション管理

⚠️ Exception Handling

このプロジェクトでは、例外は主に2つのタイプに分類されます：

HTTP Exceptions

定義: HTTPレイヤーに関連する例外で、Controllerからスローされる

ForbiddenException (403)
UnauthorizedException (401)
RouteNotFoundException (404)

使用する場合:

  • Controller内の権限チェック
  • 認証失敗
  • ルートが存在しない

Domain Exceptions

定義: ビジネスロジックに関連する例外で、Serviceからスローされる

ResourceNotFoundException (404)
ConflictException (409)
FatalErrorException (500)

使用する場合:

  • ビジネスルール違反
  • リソースが存在しない
  • 予期しないエラー

例外処理のベストプラクティス

1. Controller

HTTP例外のみをスロー（ForbiddenException、UnauthorizedException）

2. Service

ドメイン例外をスロー（ResourceNotFoundException、ConflictException、FatalErrorException）

3. Repository

例外をスローせず、nullまたは空のコレクションを返す

4. トランザクション

常に例外をキャッチしてロールバックし、その後ドメイン例外を再スローする

🔄 リクエスト処理の流れ

例: 新しいPostの作成

1. HTTP Request - POST /api/v1/post
2. Route - PostController@store
3. Controller - 権限チェック、バリデーション
4. Request - バリデーション実行
5. Service - ビジネスロジック実行
6. Repository Interface - 契約定義
7. Repository - DB操作実行
8. Model - Eloquentモデル
9. Service - 関連データロード
10. Resource - JSONフォーマット
11. Controller - レスポンス返却
12. HTTP Response - クライアントへ返却

コードフローの例

1. Controller (HTTP Layer)

// app/Http/Controllers/PostController.php
public function store(CreatePostRequest $request): PostResource
{
    // HTTP関心事: 権限チェック
    if (!RolePermissionService::isAcceptable(...)) {
        throw new ForbiddenException(...);
    }
    
    // データの抽出
    $inputs = $request->getValidatedParams();
    $adminUuid = $this->getAuthorizedAdminId();
    $userId = $this->getAuthorizedUserId();
    
    // Serviceに委譲
    $post = $this->postService->createPost($inputs, $adminUuid, $userId);
    
    // レスポンスのフォーマット
    return new PostResource($post);
}

3. Service (Business Logic Layer)

// app/Services/PostService.php
public function createPost(array $params, string $adminUuid, int $userId): Post
{
    // ビジネスルール: ポスターの確認
    $poster = $this->posterRepository->getPosterByUserId($userId, $adminUuid);
    if (!$poster) {
        throw new ResourceNotFoundException(...);
    }
    
    try {
        $this->postRepository->beginTransaction();
        
        $post = $this->postRepository->create(new Post(), $params);
        $this->associateMediaWithPost($post->id, $params['media_ids'] ?? []);
        
        $this->postRepository->commit();
    } catch (ConflictException|ResourceNotFoundException $e) {
        $this->postRepository->rollback();
        throw $e;
    } catch (\Exception $e) {
        $this->postRepository->rollback();
        throw new FatalErrorException();
    }
    
    return $post;
}

4. Repository Interface (Abstraction)

// app/Repositories/PostRepositoryInterface.php
interface PostRepositoryInterface extends RepositoryInterface
{
    public function getPost(string $id, string $adminId): ?Post;
    public function getPosts(array $params): iterable;
    public function getPostTotal(array $params): int;
}

5. Repository (Implementation)

// app/Repositories/PostRepository.php
class PostRepository extends Repository implements PostRepositoryInterface
{
    public function getPost(string $id, string $adminId): ?Post
    {
        return Post::query()
            ->where('admin_uuid', '=', $adminId)
            ->where('id', '=', $id)
            ->first();
    }
}

// app/Models/Post.php
class Post extends Model

    public function poster(): BelongsTo

        return $this->belongsTo(Poster::class);

💡 ベストプラクティス

1. Dependency Injection

常に依存性注入を使用して依存関係を注入する

// ✅ Good
public function __construct(
    private PostRepositoryInterface $postRepository
) {}

// ❌ Bad
$this->postRepository = new PostRepository();

2. Interface Segregation

Serviceは実装ではなく、インターフェースにのみ依存する

3. Single Responsibility

各クラスは単一の責任のみを持つ

  • Controller: HTTP関心事のみを処理
  • Service: ビジネスロジックのみを処理
  • Repository: データアクセスのみを処理
  • Resource: レスポンスのフォーマットのみ

4. Exception Handling

  • Controller: HTTP例外のみをスロー
  • Service: ドメイン例外をスロー
  • Repository: 例外をスローせず、nullを返す

5. Transaction Management

  • Serviceのみがトランザクションを管理
  • 例外が発生した場合は常にロールバック
  • ドメイン例外を再スローし、予期しないエラーをラップ

6. Testing

  • ServiceテストでRepository Interfaceをモック
  • ControllerテストでServiceをモック
  • 各レイヤーを独立してテスト

🎓 結論

Layered Architecture + Repository Patternを使用したClean Architectureは、以下を実現します：

🔀 関心の分離

各レイヤーは特定の側面のみを処理

🔧 保守性

1つのレイヤーの変更が他のレイヤーに影響しない

✅ テスト容易性

モッキングを通じて各レイヤーを独立してテスト可能

📈 拡張性

実装を変更してもServiceに影響しない

📝 コードの明確性

各クラスが明確な責任を持ち、読みやすい

上記の原則とルールに従うことで、コードベースは保守性、拡張性、テスト容易性が向上します。
